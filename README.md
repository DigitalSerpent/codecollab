

# Code Collab 
---
Асинхронная платформа для распределенного совместного редактирования исходного кода в режиме реального времени с изолированным runtime-окружением для безопасного исполнения пользовательских сценариев

## Архитектурный стек и спецификация

* **Primary Backend Application:** .NET 10 / ASP.NET Core (Razor Pages Core)
* **Data Access Layer (DAL):** Entity Framework Core / LINQ / SQLite ORM
* **Real-Time Gateway (Stateful):** Python 3.13 / FastAPI / Uvicorn (ASGI)
* **Frontend Layer:** Vanilla JS (ES6+) / Monaco Editor API / CSS3 Grid & Flexbox
* **Virtualization & Sandbox:** Docker Engine API / Linux IPC (POSIX)

## Топология компонентов и межсервисное взаимодействие

Система делится на два независимых слоя для изоляции потоков данных и оптимизации пропускной способности (Throughput):

* **Monolithic Core Server (ASP.NET Core):** Выступает в роли Stateless-контроллера бизнес-логики. Обеспечивает сессионную аутентификацию на базе In-Memory Cache, криптографическое хэширование паролей (алгоритм `BCrypt`), управление транзакциями в реляционной СУБД SQLite, менеджмент токенов доступа и персистентное хранение файловых сущностей
* **Real-Time Notification Service (FastAPI):** Развернут как асинхронный Stateful-микросервис. Обслуживает дуплексные WebSocket-сессии (`wss://`) для низкоуровневой широковещательной рассылки (Broadcasting) координат курсоров участников, состояние активных подключений инкапсулировано внутри RAM-структур данных (`Dict[str, Dict[str, WebSocket]]`), полностью разгружая дисковую подсистему основного сервера
* **Isolated Execution Engine (Docker Sandbox):** Подсистема безопасной интерпретации недоверенного кода. Принимает JSON-сериализованные DTO (Data Transfer Objects) через REST API, генерирует уникальный UID сессии, аллоцирует временные файлы во внутреннем томе хоста и инициирует эфемерный Docker-контейнер `code-collab-runner`. Исполнение сценариев (Python, Node.js, Bash...+(в реализации)) изолировано на уровне ядра Linux и ограничено контекстом `USER sandbox`

## Схема реляционных сущностей (СУБД SQLite)

* `Users` — атрибуты субъектов, хэшированные аутентификационные маркеры, метаданные кастомизации
* `Rooms` — идентификаторы сессий совместной работы, внешние ключи владельцев (`OwnerId`), уникальные инвайт-токены
* `RoomParticipants` — таблица сопряжения отношений многие-ко-многим (Many-to-Many). Применена частичная денормализация данных (UserName, Avatar, Cursor) для минимизации операции `JOIN` и обеспечения высокой скорости чтения (O(1)) при регулярном поллинге списка участников
* `RoomFiles` — персистентная иерархия файлов комнат (ассоциирована с внешним ключом `RoomId` с каскадным удалением `ON DELETE CASCADE`)
* `ChatMessages` — хронологический лог текстового трафика комнат, индексированный по временной метке (`Timestamp`)

## Особенности оптимизации

* **Middleware Pipeline Configuration:** В конвейере ASP.NET Core вызовы middleware перестроены в строгой последовательности: распределенный кэш памяти и сессии (`UseSession`) инициализируются до прохождения авторизационных фильтров (`UseAuthorization`), что гарантирует доступность контекста пользователя (`HttpContext.Session`) во всех REST-контроллерах.
* **Data Type Synchronization:** Параметры WebSocket-путей (Room/User ID) на стороне Python типизированы как `str`. Это предотвращает рассинхронизацию (Type Mismatch) и падение обработчиков в `422 Unprocessable Entity` при генерации фронтендом динамических UUID или строковых JS-маркеров.
* **Network Protocol Separation:** Разделены транспортные каналы. Передача контента файлов, удаление, чат и запуск терминала реализованы через стандартные асинхронные HTTP POST/PUT/DELETE контроллеры (AJAX/Fetch), тогда как WebSocket-протокол монопольно выделен под трансляцию высокочастотных потоковых событий изменения координат курсора.
